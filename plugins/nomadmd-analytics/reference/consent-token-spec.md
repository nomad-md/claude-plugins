# Cross-Domain Consent Token (Option 2)

> Lets a brand's marketing site pass a user's **marketing-consent** decision to
> checkout-web across domains (brand domain → NomadMD domain), so the Tier-2 consent
> gate (`client-architecture.md` §4) opens per the brand-collected consent — no second
> banner. Ships with the phase-2 client build; additive to the consent gate already there.
> Works on the current NomadMD-domain hosting; superseded by native CMP inheritance once a
> brand-subdomain build exists (that's a separate plan).

## Scope — what this gates (and what it doesn't)

This token resolves the **Tier-2 gate only**: GTM container injection + the
`window.dataLayer` pushes that feed the brand's GTM tags/pixels (the browser
marketing path). It does **not** gate Tier 1 — **Segment analytics.js and Datadog RUM
fire regardless of this consent** (first-party analytics; no consent gate in this design).

**Known, accepted limitation (decision 2026-06-16):** the *server-side* ad-conversion
path — Segment **cloud-mode** destinations in the brand's workspace forwarding
`Order Completed` to Meta CAPI / TikTok Events / GA4 MP — is **not** consent-gated in this
build, by decision. A user who denies marketing consent has their **browser** pixel
suppressed (this token) but the **server-side** conversion still delivers to the ad
platforms. This is an accepted tradeoff for now; revisit if an ad platform's or
jurisdiction's consent requirements force server-side parity (would require passing the
consent decision to the server via `createAppointmentRequest` and a destination-filter /
withhold rule on the ad-destination forwarding).

## Why a signed token (not a plain flag)

A forged `?consent=1` would cause the brand to process a user's data through ad pixels
**without valid consent** — a compliance liability for the brand, not just a nuisance. So
the consent must be **cryptographically asserted by the brand's consent system**, not by
whatever's in the URL. A signed token gives that: we can state consent came from the
brand, carried an expiry, and wasn't tampered with.

## Token format — a JWT (HS256)

A standard JWT so any brand can sign it with off-the-shelf libraries. Claims:

```jsonc
{
  "mkt":  1,            // marketplace id — binds the token to one brand
  "mktg": true,         // marketing consent decision (true = granted, false = denied)
  "iat":  1781300000,   // issued-at (unix seconds)
  "exp":  1781300300    // expiry — iat + 300s (5 min; it's a click-through, should be immediate)
}
```

Signed **HS256** with the brand's per-marketplace **consent secret** (below). Passed on the
checkout entry URL as **`nmd_ct`**:

```
https://checkout.nomadmd.app/<marketplace>?nmd_ct=<jwt>
```

## The per-marketplace secret

- Lives on the **`marketplaces`** table as an `encryptedKeys` FK
  (`consent_token_secret_id`, mirroring the existing `reviewsIoKeyId` pattern) —
  **with the other consent/GTM config** (`gtm_requires_consent`, `gtm_data_tier`,
  `gtm_container`), NOT on `segmentIntegrations`. It is a **consent-gate credential**
  (it governs whether the brand's GTM tags fire), not a Segment source key. Configured on
  the **GTM/consent admin page (`integrations/gtm.tsx`)**, next to the consent toggle and
  data tier — not on the Segment source page.
- A 32-byte random secret, generated by us (`openssl rand -hex 32` — the resulting
  64-char hex string is the secret, used verbatim by both sides), **shared with the
  brand out-of-band** via a secure channel (password-manager share / one-time secret
  link — never email in the clear, never a URL). They put it in *their* server env to
  sign tokens. It is a signing secret, never exposed client-side on either domain.
- Rotatable: changing it in the admin UI invalidates old tokens (acceptable — tokens are
  5-minute-lived anyway).

## Brand side (what the brand implements)

On the "Book now" click-through, the brand's **server** mints a JWT and appends it. Their
CMP supplies the consent value. Node example:

```js
import jwt from 'jsonwebtoken';
const token = jwt.sign(
  { mkt: 1, mktg: userMarketingConsent },           // from the brand's CMP
  process.env.NMD_CONSENT_SECRET,                    // the shared per-brand secret
  { algorithm: 'HS256', expiresIn: '5m' }
);
res.redirect(`https://checkout.nomadmd.app/austin?nmd_ct=${token}`);
```

Must be **server-side** (the secret can't be in their client JS). If the brand has no
server at the click point, the token can be minted by their CMP's backend or an edge
function — but never with the secret in the browser.

## NomadMD side (what this build implements)

1. **Verify — runs in dispatch-api; consumer-api facades it.** The browser calls
   consumer-api's `verifyConsentToken(token: String!): ConsentResult`; consumer-api
   **delegates to dispatch-api** over the existing server-to-server dispatch link. dispatch-api
   owns the encrypted `consent_token_secret`, so it does the decrypt + HS256 verify + `exp`/`mkt`
   checks there and returns `{ marketing: Boolean }` (or `null` on any failure). **The signing
   secret never leaves dispatch-api** — not to consumer-api, not to the browser.
   *(Refines the earlier "consumer-api verifies" shorthand: consumer-api is the client-facing
   entry point, dispatch-api is the verifier — consistent with how the v2 server emitters and
   every other per-marketplace secret already live in dispatch-api. The browser-facing contract
   is unchanged.)*
2. **Apply (checkout-web).** On app load, if `nmd_ct` is present: call `verifyConsentToken`;
   on a valid result, call `setConsent({ marketing })`; then **strip `nmd_ct` from the URL**
   via `history.replaceState` so it doesn't linger in history / referrers / shares.
3. **Fallbacks (all non-trust = status quo):**
   - Absent token → no-op; the gate uses its configured default (`gtm_requires_consent`).
   - Invalid signature / expired / `mkt` mismatch → **ignore** (log, treat as absent). Never
     trust a token we can't verify.
   - `mktg: false` → honor as a **deny**: `setConsent({ marketing: false })` (discards the
     Tier-2 buffer; no GTM injection / dataLayer pushes).
4. **Audit.** consumer-api logs every verified consent receipt (`marketplace_id`, decision,
   `iat`) for compliance defensibility. (Optional: emit an internal `Consent Updated` event
   — deferred unless wanted.)

## Security & hygiene

- **HTTPS only** — it's a consent assertion.
- **Short TTL (5 min)** — a copied/shared link can't carry consent indefinitely; bounds replay.
- **`mkt` binding** — a token for brand A can't grant consent on brand B's storefront.
- **Strip from URL after read** — keep it out of history, referrer headers, and shared links.
- **No PII in the token** — only the marketplace id and the boolean decision.
- The token can only **resolve** the gate (grant or deny); it can never expand what Tier 2
  carries — the §6 minimal/commerce whitelists still bound the payload regardless.

## Scope for this build

| Piece | Where |
|---|---|
| `consent_token_secret_id` encryptedKeys FK on **`marketplaces`** (with the consent flags) + admin field on **gtm.tsx** | dispatch-api + dispatch-web |
| `verifyConsentToken`: decrypt + HS256 verify in **dispatch-api**, thin delegating facade resolver in **consumer-api** | dispatch-api + consumer-api |
| `nmd_ct` reader → verify → `setConsent` → strip URL | checkout-web (alongside the existing consent gate) |
| Brand integration doc (the recipe above) | this file — hand to brand devs |

Out of scope (future): IAB TCF / Google Consent Mode consent strings; per-category consent
(this carries marketing only, matching the `{marketing}` gate); native CMP cookie
inheritance (requires the brand-subdomain build — separate plan).
